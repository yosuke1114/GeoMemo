# 依頼の共有（CKShare）

依頼（SharedMemo）は、依頼者の Private DB のカスタムゾーン `geomemoSharingZone` に
`SharedMemo` レコードとして保存し、レコードをルートにした `CKShare` で相手に渡す。
SwiftData の `SharedMemo` は送受信した依頼の端末側キャッシュ。

関連コード: `CKShareService.swift`, `SharingPolicy.swift`（判断ロジック）, `ShareMemoSheet.swift`,
`ShareActivityPresenter.swift`, `WatchDashboardView.swift`（依頼者）, `ContentView.swift`（受信者の同期）。

決定の経緯は [ADR-0004](adr/0004-private-ckshare-sharing.md)。

## 共有の作り方（2.1 以降）

共有は **非公開**（`publicPermission = .none`）。共有 URL を開いて参加できるのは、
依頼者が参加者として加えた人だけ。URL が転送・漏えいしても、第三者は参加できない。

| 送り先 | 方法 |
|---|---|
| フレンド | フレンドの userRecordID から `CKContainer.shareParticipants(forUserRecordIDs:)` で参加者を引き、`.readWrite` で共有に加えて保存。共有 URL を共有シート（メッセージ・LINE 等）で送る |
| 新しい相手（「リンクで送る」） | `NSItemProvider.registerCKShare(_:container:allowedSharingOptions:)` を `UIActivityViewController` で表示。`CKAllowedSharingOptions(.readWrite, .specifiedRecipientsOnly)`、参加者による再招待・アクセス要求は不可。共有シートで選んだ相手（メッセージ・メールの宛先）をシステムが参加者に加える |
| フレンドの参加者を引けなかった場合 | 「新しい相手」と同じ招待の流れに切り替える |

- 送ったかどうかは `ShareSheetCompletionTracker` で決める（下の「送ったかどうかの判定」）。
  送らずに閉じたことが確かなときだけ、作ったレコードと共有をサーバから消す。
- `UICloudSharingController` は使わない（保存済みの共有を渡すと完了コールバックが来なかったため）。
- 共有の題名（`CKShare.SystemFieldKey.title`）は固定の「geomemo の依頼」。リンクのプレビューに依頼の内容を出さない。
- `encryptedValues` は CloudKit 上での保存時暗号化で、**参加者には復号された値が見える**。
  内容を守っているのは「参加者を限定していること」。

### 送ったかどうかの判定

iOS 13 以降、共有シートで「メッセージ」「メール」等を選んで作成画面をキャンセルすると、共有シートは開いたまま
`completionWithItemsHandler` が `completed == false`（`activityType` は選んだもの）で呼ばれる。ユーザーはそのまま
別のアプリで送れるため、最初の `completed == false` で消すと、相手に届いたリンクが無効になる。

| 完了ハンドラ・共有シート | 判定 | 依頼 |
|---|---|---|
| `completed == true` | 送った | ローカルに保存する |
| `activityType == nil`, `completed == false`（何も送らずに閉じた） | 送らなかった | サーバのレコード・共有を消す |
| `activityType != nil`, `completed == false` | まだ決めない | 次の呼び出しを待つ |
| 共有シートが閉じて 2 秒待っても決まらない | 分からない | 消さずにローカルに保存し、見守り画面に「未送信」と出す |

- 「分からない」の後に `completed == true` が届いたら（作成画面が共有シートを閉じた後に出る送り方）、「未送信」を外す。
- 共有シートが閉じたことは `viewDidDisappear` かつ `isBeingDismissed` で見る（作成画面を上に重ねたときは閉じたことにしない）。
- 「未送信」の依頼は、見守り画面の長押しで「リンクを送り直す」か「削除」を選べる。削除は、所有者以外に受諾した人・
  招待中の人がいなければサーバから消し、いれば（リンクが届いているかもしれないので）取り消しにする。
  受け取った人が分かったら（共有の受諾済みの参加者が見つかったら）「未送信」を外す。

#### サーバに残ったレコードの後片付け

`UnsentShareStore`（App Group の UserDefaults、端末ごと）に、共有シートで送る依頼を表示前に記録しておく。

- 送らなかった依頼の削除は、項目ごとの結果を確認する（既に無いものは成功）。失敗はログに出し、記録を残して
  次回のアクティブ化で消し直す。
- 共有シートの表示中にアプリが終了されると、記録が「表示中」のまま残る。10 分（`UnsentShareCleanupPolicy.orphanAge`）
  過ぎた記録は、次回のアクティブ化で後片付けする。
- **受諾した人・招待中の人がいる共有は消さない。** 例外は「送らなかった」と分かっている依頼で、フレンドに送るとき
  自分で加えた相手（URL を送っていないので届いていない）が招待中のままの場合だけ。結果の分からない依頼には例外を使わない。
- 参加者がいて消せなかった依頼は、サーバから読み直してローカルに「未送信」として残す。

### リンクの送り直し

`CKShareService.resendMethod(for:)` / `ShareResendMethod.decide`:

- 招待済み（pending / accepted）の相手がいる非公開の共有 → 同じ URL を送る（開けるのは招待済みの相手だけ）。
- 招待済みの相手がいない非公開の共有 → システムの共有シートで招待し直す。
- 旧版で作った公開リンクの共有 → 権限は変えず同じ URL を送る（下の「制限事項」）。
- 公開リンクには戻さない。

## 参加者が書ける値の扱い

参加者は `.readWrite`（状態の更新に必要）なので、レコードの全フィールドを書き換えられる。依頼者側は次のようにする。

- **受信者の本人確認**: レコードの `recipientRecordID` / `recipientName` ではなく、共有の参加者
  （`CKShare.participants` のうち、受諾済み・所有者以外・userRecordID が分かる人）から決める
  （`SharedMemoRecipientResolver`）。表示名は CloudKit の名前を優先し、無ければ本人がレコードに書いた名前。
- **フレンドの自動登録**: 受信者が新しく決まったときだけ登録する（`FriendAutoRegistrationPolicy`）。
  - 旧版の公開リンクの共有（`publicPermission != .none`）では登録しない。誰でも参加でき、受信者の選び方
    （レコードで名乗っている参加者を優先）も参加者に操作されうるので、受信者は表示にだけ使う。
  - ユーザーが削除したフレンドは、削除の記録（`FriendTombstoneStore`、App Group の UserDefaults、削除した日時付き）に
    あれば登録しない。
  - 削除の記録は、ユーザー自身の操作で外す。受信側は共有の受諾で所有者を外す。依頼者側は、削除した**後に**
    招待（「リンクで送る」）で送った依頼を、その人が受け取ったときに外して登録し直す。送った日時は端末で記録した
    `SharedMemo.createdAt` を使う（相手が書けるレコードの `createdAt` は使わない）。
- **本人確認できていないフレンド**: 旧版は、参加者が書けるレコードのフィールドからフレンドを登録していたため、
  「母」という名前で別人の ID を持つフレンドがありうる。非公開の共有では、フレンドを選ぶとその ID の人だけを招待する。
  - CloudKit の情報で本人を確かめたフレンドの ID を `VerifiedFriendStore`（App Group の UserDefaults）に記録する。
    共有の受諾（所有者）・非公開の共有の受諾済みの参加者から新しく登録したとき、または既存のフレンドの ID に
    CloudKit の名前が分かったとき（名前をそれに合わせる）。SwiftData のスキーマは変えない。
  - 記録に無いフレンドは「未確認」と表示し、依頼を送る前に確認のダイアログを出す。
- **タイトル・期限**: 自分が送った依頼には、サーバの値を反映しない（`SharedMemo.apply`）。
- **状態**: 後戻りさせない（active → fired → completed、cancelled は active / fired から）。索引の古い
  CKQuery の結果で、手元の取り消し・完了が戻らないようにする。サーバの状態が終点（completed / cancelled）なら
  何も書かない（オフラインで溜まった取り消しが、その後の完了を上書きしない）。取り消しが書き込まれなかったときは、
  依頼者側の表示をサーバの状態に合わせる。
- **通知文**: 依頼者への購読通知は固定の文言（`SHARED_MEMO_ARRIVED` / `SHARED_MEMO_COMPLETED`）。
  レコードのフィールドを通知文に差し込まない（旧版の購読 `requester-*-v1` は削除し、`-v2` を登録する。
  下の「購読の移行」）。

## 依頼者への通知が重ならないように

購読は `status == fired` / `status == completed` の `firesOnRecordUpdate`。この状態のレコードが更新されるたびに
通知が出るため、到着・完了後はレコードを書き換えない。

- 状態の書き込み（`updateStatus`）は、サーバの状態が同じか先へ進んでいれば何もしない（再送キューのリトライや二重の発火）。
- 送信後の編集・リンクの送り直し・キャンセルは、監視中（active）の依頼だけ。編集はサーバ側でも active を確認する。
- 受信者名の書き込み（`claimRecipient`）は、active で受信者が未定のときだけ。初回の取り込みでも行う。
- 受信側は、active でない依頼のジオフェンス進入を無視する。

## 購読の移行（-v1 → -v2）

- 起動後のアクティブ化で、`-v2` が無ければ作り、`-v1` があれば消す（1 回の `modifySubscriptions`）。項目ごとの結果を
  確認し（消そうとした購読が既に無いのは成功）、すべて成功したときだけ、その起動では済みにする。
- 同じ Apple ID に旧版の端末があると、旧版は起動のたびに `-v1` を作り直す。`-v1` を残すと、旧版の端末が無くなるまで
  通知が二重に届き続け、相手が書いた名前も通知文に出続けるため、**見つけるたびに消す**方を選んだ
  （残す方が二重通知は長く続く）。加えて、`-v1` の通知を受けたら（フォアグラウンドでは表示せず、
  バックグラウンドでは content-available で起こされて）その場で `-v1` を消し、二重に届く期間を短くする。
- 旧版の端末が `-v1` を作り直してから、新しい版の端末が通知を受けて消すまでの間は、二重に届く（制限事項）。

## 本文（SharedMemoNoteStore）

- 依頼者: 編集画面を開くたびにサーバから本文を読む。読めなかったときは本文を書き込まない（空で上書きしない）。
  端末のキャッシュに本文があればそれを出すが、書き換えたときだけ保存する（古い本文でサーバの新しい本文を上書きしない。
  `SharedMemoNoteEditPolicy`）。
- 依頼者: 完了・取り消しを確認したら本文を消す。
- 受信者: 取り消しを確認したら消す。完了は完了から 24 時間だけ残す（「到着で自動完了」は到着と同時に完了になるため、到着後に本文を読めるように）。
- 送らずに閉じた依頼は、サーバのレコード・共有ごと消す（上の「送ったかどうかの判定」）。

## 受信者の画面（受け取り画面・バッジ・簡易表示）

- リンクを受諾すると（到着の監視は今まで通り受諾した時点から）、取り込みの後に受け取り画面（`ReceivedSharedMemoDetailView` の
  `isArrival`）をシートで出す。依頼者・「伝わるのは到着と完了だけ」の説明・足りない許可の案内・「名前を伝える」（プロフィールが無いとき・任意）・「断る」。
  何を出すかは `RecipientLogic.swift`（`ArrivalResolver`、`ReceivedArrivalContent`）が決める。受諾した共有は
  `CKShare.Metadata.hierarchicalRootRecordID` のレコード名で探し、取れなければ依頼者（ゾーンの所有者）で探す。
- この端末で受諾したときだけ自動で出す。SwiftData の iCloud 同期で別の端末から来た依頼は出さず、地図左上のバッジの「新着」になる。
- 地図の左上に「依頼 n」のバッジ（到着待ち・到着済みが 1 件以上のとき）。押すと「受信した依頼」の一覧。
- 自分のメモも送った依頼も無く、受け取った依頼だけある人は、下部の「ADD MEMO」の代わりに受信した依頼のカードを出し、作成は「＋」に残す。
- 既読（バッジの「新着」）は App Group の UserDefaults（`receivedRequestSeen`、種まき済みの印 `receivedRequestSeenSeeded`）に端末ごとに記録する。
  iCloud では同期しないので、別の端末では同じ依頼が「新着」と出る。この版の最初の起動で、その時点の依頼はすべて既読にする。
- 「断る」で共有から抜けるのに失敗したときは、断ったレコード名（と共有ゾーンの所有者）を App Group の UserDefaults
  （`declinedReceivedRequests`、`DeclinedRequestStore`）に残す。同期ではそのレコードを取り込まず監視もせず、同期のたびに抜け直しを再試行し、
  成功したら記録を消す。同じ依頼を受諾し直したときも消す（もう一度受け取るには送り直してもらう）。
- 受諾の失敗は `ShareAcceptFailure` で分類して文を出し分ける（未サインイン・通信・取り消し／削除済み・招待されていない・その他）。
- 期限切れの依頼には「期限切れ」と表示するが、到着の発火の条件は変えていない（期限・時間帯を見ずに発火する）。

## 制限事項

- **旧版（2.0.1 以前）で作った共有は公開リンクのまま。** `publicPermission` を `.none` に変えると、公開リンクから
  参加した受信者を CloudKit が外してしまうため変更しない。これらの依頼は、URL を知っていれば誰でも参加して
  内容を読み書きできる状態が続く。依頼が終われば影響はなくなるので、気になる場合は依頼者が取り消して送り直す。
- 招待（新しい相手）は、共有シートで宛先が分かる送り方（メッセージ・メール等）が前提。宛先の分からないアプリで
  送ると、招待した相手が参加者にならず開けないことがある。その場合はフレンドとして送るか、メッセージで送る。
- 1 件の依頼に複数の人を招待できてしまう（システムの共有シートで複数人を選んだ場合）。依頼者側の受信者は
  参加者のうち 1 人（レコードで名乗っている人、いなければ ID 順の先頭）として表示する。到着・完了は誰のものでも反映される。
- 削除したフレンドの記録は端末ごと（iCloud で同期しない）。別の端末では、新しく受信者が決まった依頼から再登録されうる。
- 削除したフレンドを依頼者側で登録し直すのは、削除後に「リンクで送る」で新しく送った依頼を受け取ったときだけ。
  削除前に送った依頼の「リンクを送り直す」（招待し直し）で受け取っても登録し直さない。
- 「未確認」「未送信」の記録も端末ごと。SwiftData の同期で別の端末に来た依頼・フレンドには付かない
  （フレンドは別の端末では「未確認」と出ることがある）。
- **購読の移行は、同じ Apple ID のすべての端末を新しい版にするまで終わらない。** 旧版の端末が起動するたびに旧版の
  購読（`-v1`）が作り直され、新しい版の端末が消すまでの間、到着・完了の通知が二重に届き、`-v1` の通知文には
  相手がレコードに書いた名前が入る。すべての端末をアップデートするよう案内する。
- 受信者がレコードに書く表示名（`recipientName`）は、CloudKit の名前が無いときの表示にだけ使う。本人の自己申告である点は変わらない。
- **Apple Watch との同期。** 受け取った依頼の写し（`SharedMemo`）・プロフィール・フレンドは、本人のプライベート DB
  経由で Watch のストアにも同期される（Watch も iPhone と同じ 5 モデルのスキーマで開くため）。Watch の画面には
  出さず、Watch 側で依頼を扱う操作もない。共有 DB（CKShare の受け取り側）には Watch はアクセスしない。
  Watch で作ったメモの監視（ジオフェンス）は、iPhone でアプリを開くまで登録されない。

## CloudKit スキーマ

この変更で新しいフィールド・レコードタイプは追加していない（Production への再 Deploy は不要）。
購読は ID を `-v2` に変えて作り直す（スキーマではない）。

## 実機での確認手順（2 つの Apple ID）

シミュレータでは CloudKit の共有を確認できないため、端末 A（依頼者）と端末 B（受信者）で行う。
両端末とも Development 環境のビルドで、iCloud にサインインしておく。依頼者（A）はプロフィール（表示名）を設定しておく。
受信者（B）は、設定していなくても依頼を取り込める（下の 4a）。可能なら第三の Apple ID の端末 C も用意する。

### 1. 新しい相手へ招待で送る

1. A: メモ詳細 →「依頼する」→「リンクで送る」→「依頼を送る」。共有シートの見出しが「geomemo の依頼」で、
   メモのタイトルが出ていないこと。
2. A: 共有シートを閉じる（送らない）。CloudKit Dashboard の A の `geomemoSharingZone` にレコード・共有が残っていないこと。見守り画面に出ないこと。
2a. A: 共有シートで「メッセージ」を選び、作成画面をキャンセル → 共有シートが開いたままで、そのまま別のアプリ（または
   もう一度メッセージ）で送る → 見守り画面に出て、B がリンクを開けること（レコードが消えていないこと）。
2b. A: 作成画面をキャンセルしてから共有シートを閉じる → レコード・共有が消えること。
2c. A: 共有シートの表示中にアプリを終了 → 10 分以上たってから起動 → 参加者のいないレコード・共有が消えること。
   メッセージで送った直後に終了した場合は、消えずに見守り画面に「未送信」として出ること。
3. A: もう一度送り、メッセージで B の宛先を選んで送る。見守り画面に「リンクで共有」として出ること。
4. B: メッセージのリンクを開いて受け取る。依頼が一覧に出て、本文が見られること。設定のフレンドに A が出ること。
4a. B（プロフィールを設定していない状態）: 同じようにリンクを開いて受け取る → 依頼が取り込まれ、地図で監視される。
   A の見守りでは、受信者名が CloudKit の名前（無ければ「相手」）で出ること。B が後でプロフィールを設定すると、
   次の同期で（監視中の依頼に限り）名前が書き込まれる。
5. A: 見守りで更新 → 受信者名が B の名前に変わり、フレンドに B が出ること。
6. C: 同じリンクを C に転送して開く → 参加できない（アクセス権が無い旨の表示）こと。
7. CloudKit Dashboard で共有の `publicPermission` が none、参加者が A（owner）と B だけであること。

### 2. フレンドへ送る

1. A: フレンドの B を選んで送る。共有シートでコピーまたはメッセージ送信。
2. B: リンクを開いて受け取れること。C に URL を転送して開いても参加できないこと。
3. A: 見守りで受信者が B のまま、フレンドが重複しないこと。

### 3. 到着・完了の通知

1. B: 依頼の場所へ入る（またはシミュレート）→ A に「依頼の相手が場所に到着しました」が 1 回だけ届くこと。
   通知文に名前やレコードの値が入っていないこと。
2. B: アプリを何度か前面に戻す／機内モードで到着→復帰させて再送させる → A に到着通知が重ねて届かないこと。
3. B:「完了」→ A に「依頼の相手が依頼を完了しました」が 1 回だけ届くこと。
4. 「到着で自動完了」の依頼: B が到着 → A に完了通知が 1 回。B は到着後に本文を読めること。

### 4. 編集・送り直し・取り消し

1. A: 監視中の依頼を長押し →「内容・期限を編集」。本文欄にサーバの本文が出ること（送った端末と別の端末、または
   再インストール後でも）。オフラインで開くと「本文を読み込めませんでした」になり、保存しても B の本文が空にならないこと。
2. A: 到着済み・完了の依頼では、長押しメニューに編集・送り直し・キャンセルが出ないこと。
3. A:「リンクを送り直す」→ 招待済みの相手がいれば URL、いなければ招待の共有シートが出ること。C に送っても参加できないこと。
4. A: 監視中の依頼を「キャンセル」→ B の次回同期で取り消しになり、監視が止まり、本文が消えること。

### 4b. 受け取り画面（P-2）

1. B（オンボーディング済み）: リンクを開く →「依頼を受け取っています…」→ 受け取り画面（依頼者の名前・場所・本文・3 項目）。
2. B（アプリを入れた直後）: リンクから起動 → オンボーディングに「依頼が届いています」→ 終えると受け取り画面。「常に」を「あとで」にすると案内の箱が出ること。
3. A が受諾前に取り消す → B がリンクを開くと「取り消しました」の文。A が削除したリンクは「取り消されたか、もうありません」。
4. A から 2 件続けて送り、B が続けて開く → 一覧が出て、バッジが「依頼 2」。
5. B が受諾した後に A が取り消す → トースト、バッジ・カードから消える。
6. B:「この依頼を断る」→ B から消える。A の側には残り、A に通知が出ないこと。
7. 同じ Apple ID の別の端末では、受け取り画面が自動で出ず、バッジに「新着」が付くこと。
8. 受信だけの B で、下部が受信した依頼のカードと「＋」になること。

### 5. フレンドの削除

1. A: フレンド管理で B を削除 → 見守りで更新しても B が戻らないこと。
2. A: B から新しい依頼を受け取る（共有を受諾）→ B がフレンドに戻ること（ユーザー自身の操作のため）。
3. A: B を削除した後、「リンクで送る」で B に新しく送り、B が受け取る → 見守りで更新すると B がフレンドに戻ること。
4. 2 台の端末で同じ相手が重複登録された状態で、フレンド管理を開く → 1 件にまとまること。

### 5a. 未確認のフレンド

1. 旧版で登録したフレンドがある状態で新しい版を入れる → フレンド管理・依頼の送り先に「未確認」と出ること。
2. 未確認のフレンドを選んで「依頼を送る」→ 確認のダイアログが出ること。キャンセルで送られないこと。
3. そのフレンドから依頼を受け取る（または相手が依頼を受け取り CloudKit の名前が分かる）→「未確認」が消え、
   名前が CloudKit の名前になること。

### 6. 旧版で作った共有

1. 2.0.1 で作った依頼（公開リンク）を、新しい版の A で「リンクを送り直す」→ 同じ URL が送られ、B の参加が切れないこと。
2. CloudKit Dashboard で、その共有の `publicPermission` が変わっていないこと。
3. 公開リンクの依頼を、フレンドでない C が受け取る → A の見守りに C の名前は出るが、A のフレンドに C が増えないこと。

### 6a. 購読の移行（旧版と新しい版の端末が同じ Apple ID）

1. 端末 A1 を新しい版、A2 を 2.0.1 にする。A2 を起動 → Dashboard の購読に `-v1` が作られること。
2. B が到着 → A1 ではフォアグラウンドで `-v1` の通知が出ず、その後 Dashboard から `-v1` が消えていること。
3. A2 をアップデート → 以後 `-v1` が作られず、通知が 1 回だけ届くこと。

### 6b. 取り消しと完了が重なったとき

1. A: オフラインで監視中の依頼をキャンセル（再送キューに入る）→ その間に B が完了 → A をオンラインに戻す →
   A の見守りで完了と出ること（取り消しで上書きされないこと）。

### 6c. 本文の編集（キャッシュ）

1. A: オフラインで編集画面を開く（本文のキャッシュがある端末）→ キャッシュの本文と注意書きが出ること。
2. 本文に触れずにタイトルだけ変えて保存（オンラインに戻して）→ 別の端末で編集した新しい本文が残っていること。

### 7. 通知のデリゲート

1. アプリを前面にしたまま通知を受ける → バナーが出ること。
2. 通常メモの通知の「5 分後」「完了」アクション、通知タップでメモが開くこと（クラッシュしないこと）。
